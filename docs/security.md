# セキュリティ設計

この文書は公開可能な範囲で、実装時に採用している防御方針を説明します。秘密値、DB定義、内部識別子は記載しません。

## 認証と認可

- Supabase Authの利用者をサーバー側で検証
- リクエスト本文のユーザーIDを認可根拠にしない
- 検証済みセッションから利用者IDを取得
- 外部アカウント操作前に所有者を照合
- 運営者専用APIでは利用者に加えて運営者権限を確認

## OAuth

- stateをサーバーシークレットで署名
- state、短時間Cookie、ログイン利用者を照合
- コールバックURLを事前登録した値に固定
- OAuthトークンを画面・通常ログ・AI入力へ含めない
- 解除時は関連する保存データもサーバー側で処理

## データベース

- 公開スキーマの重要テーブルでRLSを有効化
- anon / authenticatedの不要な権限を剥奪
- 管理者キーはサーバー専用環境変数として管理
- SECURITY DEFINER関数はsearch_pathと実行権限を限定
- ユーザー削除時の関連データ削除をDB側でも保証

## API

- 更新系リクエストでOriginを確認
- 入力サイズ、型、文字列長を検証
- Cronは専用Bearerシークレットを要求
- 開発用エンドポイントは本番で404を返す
- エラー応答に内部例外や秘密値を含めない

## AI

- 外部サービス由来の文字列を信頼できない入力として扱う
- システム指示とユーザーデータを分離
- 構造化出力を型検証してから利用
- 回数上限と全体予算をサーバー側で管理
